# Ежемесячный отчёт ресторана — спецификация

Контекст для отдельного чата: написать единый скрипт-генератор месячного
PDF-отчёта. Эталон согласован владельцем на июле 2026 (Ташкент):
`~/Downloads/itogovyi-otchet-iyul-2026.pdf` (12 страниц). Рабочие
скрипты-прототипы, из которых собран эталон, лежат в
`D:\seasons\backend\scripts\scratch_report_v2_*.py` (sales, purchases,
stock, writeoffs, fot, assemble) — их логику переносим в один
параметризованный генератор.

## Цель и принцип

- Один вызов: `python -m src.cli.monthly_report --restaurant-id <uuid>
  --year 2026 --month 7` → PDF в указанную папку.
- Отчёт «человеческий»: его читает владелец/управляющий/партнёры, он может
  уйти команде. Поэтому: без внутреннего брендинга («Сезоны» не упоминать),
  без персональных зарплат (только группы ФОТ), без служебной механики
  (слово «сторно» в тексте не употреблять).
- Долгосрочная цель: отчёт формируется ИЗ ДАННЫХ ДАШБОРДА (REST API),
  а не прямыми запросами. Сейчас часть данных в API отсутствует — см.
  таблицу источников: где API готов, ходим в API; остальное — временно
  напрямую (БД/OLAP iiko), помечено как долг.

## Структура документа

Титул: «Итоговый отчёт · <месяц год>», «<BRAND> · <город>», период, валюта,
оглавление из 5 разделов.

### 1 · Продажи
- KPI-строка: выручка, чеки, гости, средний чек — каждый с % к прошлому
  месяцу.
- График «Выручка по дням»: зелёные бары, сб/вс светлее, подписи значений
  только у пиков (>=90% max) и минимумов.
- Топ-20 позиций КУХНИ по количеству: #, позиция, порций, выручка (млн),
  доля юнита %, FC %.
- Топ-20 позиций БАРА по количеству (вино включается в бар).
- Доп.страница: «Новая выпечка» (динамика новинок по неделям с даты
  запуска — новинка = первая продажа в отчётном месяце внутри группы
  «Выпечка»; для универсальности: параметр launch-date опционален,
  без него блок пропускается) и «Категории в общей выручке» (юнит,
  категория=dish_group, SKU, выручка, доля; топ-20 + «остальные»).

### 2 · Закупки
- KPI-строка: итог месяца, % к прошлому месяцу, разбивка
  кухня/бар/хозтовары, число дней с приходами.
- Сноска-сверка: сумма приходов на склады == кредиторка «Задолженность
  перед поставщиками» (обязательная валидация, расхождение — ошибка).
- График «Закупки по дням» (бары, подписи пиков).
- График «Динамика остатка склада и закупок»: сверху линия остатка
  (все склады), снизу бары закупок; вертикальная пунктирная метка даты
  инвентаризации (если была в месяце — определяется по транзакциям
  INVENTORY_CORRECTION).
- Такие же двухпанельные графики ОТДЕЛЬНО для кухни и бара
  (заголовок и график не разрывать между страницами — KeepTogether).
- Отдельной страницей: таблица «Закупки по неделям» (пн-вс, только дни
  отчётного месяца, сноска об усечении крайних недель) + «Топ-10 позиций
  по сумме закупки» с колонками ср. цена / цена прошлого месяца / Δ%.

### 3 · Склад
- KPI-строка: остаток на конец месяца по юнитам, изменение за месяц.
- График «Минусовые остатки по дням»: бары = число позиций с
  отрицательным расчётным остатком, линия (правая ось) = сумма минуса,
  метка инвентаризации.
- Таблица «Остатки на конец недель» (воскресенья + базовая точка до
  начала месяца): кухня, бар, вино, итого, минуса (позиций и сумма).
- Таблица «Замороженные позиции»: qty(конец месяца) == qty(начало)
  и стоимость > 0.5 млн; топ-12 + итоговая строка-сноска (сколько всего
  и на какую сумму).
- Правило: минусовые остатки НИКОГДА не входят в стоимость склада,
  показываются отдельно («бумажный долг учёта, а не еда»).

### 4 · Списания и потери
- KPI-строка: продуктовые списания месяца, % выручки, крупнейшая статья.
- Категории — маркерный резолвер счетов
  (`src/domain/constants.py::resolve_loss_account`); типы: spoilage, brak,
  tasting, compliment, staff, blogger, marketing, deletion, operational,
  supplies, hotel, other.
- РАСХОДНИКИ (supplies: хозка, уголь, упаковка, лёд) — отдельная
  категория, в «продуктовые потери» не входят.
- Сторно-строки (storno=True в writeoff_entries) исключаются из всех
  сумм; в тексте отчёта слово «сторно» не упоминается.
- График: горизонтальные бары категорий (без supplies).
- График: списания по дням (без supplies), метка кануна инвентаризации.
- Таблица категорий: сумма, число строк-актов, % выручки (+ строка ИТОГО
  с расходниками). Сноска про «вне категорий» = счёт «СЕБЕСТОИМОСТЬ
  ПРОДУКТОВ» (рекомендация проводить на именованные счета).
- Таблица «Топ-10 позиций в порче» + вывод о доле полуфабрикатов.

### 5 · Фонд оплаты труда
- Источник — xlsx-ведомость бухгалтера (пока вне систем; путь передаётся
  параметром; структура: листы по месяцам, два блока с повторной шапкой,
  группы = строки без должности, безымянные строки = итоги, их
  пропускать; ИТОГО сотрудника — колонка «ИТОГО»).
- Валидация: сумма по сотрудникам vs собственная строка-итог листа;
  при расхождении — предупреждение в консоль (в июле формулы листа
  не охватывали все блоки).
- KPI: итог, % к прошлому месяцу, доля выручки текущего и прошлого месяца.
- График: парные горизонтальные бары групп (текущий месяц зелёный,
  прошлый серый).
- Таблица групп: суммы, Δ%, % выручки; исчезнувшие группы строкой «—100%».
- БЕЗ имён и персональных сумм. Без аналитических выводов в сносках
  (владелец просил только цифры).

## Правила данных (общие, уже реализованы в прототипах)

- Продажи: только строки paid_sum > 0; чеки/гости — только чеки
  paid_total > 0. Юнит — resolve_unit(top_group): k/b/w; вино в отчёте
  сливается с баром.
- Спецзаказы (имя содержит «спецзаказ») исключаются из всех топов
  и категорий продаж.
- FC позиции = cost/выручка; позиции без себестоимости — «—» в колонке
  FC (не 0%). Себестоимость — учётная iiko, в шапке раздела 1 это
  оговаривается.
- Деньги: крупные суммы в млн с 1 знаком, разделитель тысяч — пробел;
  проценты с 1 знаком; валюта из настроек ресторана (Ташкент UZS,
  Бишкек KGS).
- Закупки: OLAP TRANSACTIONS, тип INVOICE, плюсовые стороны на счетах
  складов (кухня/бар/хоз.товары); кредиторка — контрольная сумма.
- Списания: таблица writeoff_entries (домен синка writeoffs).
- Склад: таблица stock_balances (ежедневные слепки).

## Источники: сейчас → цель (формирование из дашборда)

| Блок | Сейчас | Целевая ручка API |
|---|---|---|
| KPI продаж | SQL по orders/dish_sales | `GET /api/base-metrics/batch?metrics=revenue,checks,guests,avg-check` + `/snapshot` |
| Выручка по дням | SQL | `GET /api/base-metrics/revenue/series` |
| Топы позиций | SQL | `GET /api/sales` (positions: qty/revenue/cost есть) |
| Категории | SQL | `GET /api/sales` (группировка по category на клиенте) |
| Списания | SQL writeoff_entries | `GET /api/foodcost` → losses.writeoffs (уже отдаёт категории) |
| Склад: остатки | SQL stock_balances | `GET /api/stock` (частично; недельные срезы и «замороженные» — НЕТ в API, долг) |
| Минуса по дням | SQL stock_balances | нет в API — долг |
| Закупки | OLAP iiko напрямую | нет домена purchases — долг (кандидат №15 в backend-todo) |
| ФОТ | xlsx бухгалтера | вне продукта (пока) |

Когда пишете генератор: для блоков с готовой ручкой — ходить в API
(auth: POST /api/auth/login, cookie), для остальных — как в прототипах;
каждый «долг» помечать в коде TODO со ссылкой на эту таблицу.

## Вектор: «Сезоны» сами становятся этим отчётом

Скрипт-генератор — промежуточная форма. Целевое состояние: продукт умеет
то, что сейчас делает связка «скрипты + аналитик». Зафиксировано
(05.08.2026), чего не хватает, — четыре слоя, от дешёвого к дорогому:

1. **Домены.** В продукте нет половины данных отчёта: закупки (раздел 2
   целиком — прямой OLAP), инвентаризация (сличение, излишки/недостачи),
   ФОТ (внешний xlsx). Владелец читает месяц как P&L: выручка → еда →
   люди; дашборд сейчас видит только выручку и фудкост.
2. **«Месяц» как сущность.** Дашборд отвечает «как идём?» (живое,
   прогноз); отчёт — «что произошло и почему?» (закрытый период,
   каждая цифра со сравнением). Нужен режим «Июль 2026» как объект:
   открыть, пролистать, выгрузить PDF, отправить в телеграм.
3. **Стыки доменов.** Все ценные находки живут на пересечениях:
   малина = склад х ТТК х инвентаризация; рибай = закупочные цены х
   средние х недостача; американо = продажи х ТТК х кофе на складе;
   стафф-транч = списания х излишки. Страницы-силосы этого не видят.
   Решение — детерминированные правила-детекторы (уже существуют как
   скетчи: двойная жизнь карточек, разрыв «актировано/всплыло на
   инвентаризации», лаг проводок, замороженные позиции, позиции без
   ТТК) — превратить в подсистему с реестром алертов (реестр алертов
   есть в editorial-мокапе дашборда).
4. **Голос.** Сноски-интерпретации под таблицами — то, что делает отчёт
   читаемым документом. ~80% таких фраз детерминированы: порождаются
   шаблонами из правил слоя 3 («если недостачи > актированной порчи
   в N раз → фраза X») — цифры из базы, выводы из правил, без
   галлюцинаций. Оставшийся свободный нарратив — опциональный LLM-слой
   поверх готовых фактов, продукт работает и без него.

Порядок внедрения: закупки как домен → «страница месяца» с PDF-экспортом
(эта спека — её каркас, генератор станет её бэкендом) → детекторы как
подсистема → текстовый слой из правил. Инвентаризация и ФОТ — по мере
готовности клиентов делиться данными.

Стратегический смысл: «дашборд соберёт любой» — но стыки доменов,
детекторы бардака и месяц-как-документ — это ресторанная экспертиза,
которую конкурент без живого ресторана не воспроизведёт.
